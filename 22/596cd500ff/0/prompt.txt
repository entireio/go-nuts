  ## 3. Gaps
  
  **(a) A durable single writer, in core or in a relay**
  - No writer runs without a user. Writers live only as long as a WebSocket connection, and every push, maintenance included, uses the caller's bearer (ADR 0008, "Authority").
  - entiredb gives entire-api no cert-only git access.
    - `svcTokGitWorkloads` lets entire-api's certificate through on the git mount (`entiredb/internal/entireserver/svctok_listener.go:436-446`).
    - But `certOnlyGitPrincipal` grants a principal only to mirror-worker (write-mirror), entiredb, and read-any-repo workloads (`svctok_listener.go:784-803`). So entire-api still needs a bearer for git.
    - Both a service-identity fetch and a service-identity push would need an entiredb change. Alternatively, the writer could use a minted token, through STS like `changeforge` does, with a new reason that entiredb's Core must admit.
  - Leases are cell-local Postgres rows, and `LapsedStrataWriters` reads only the local table. A writer in another cell is invisible: the only cross-cell safety is `StaleBlockerAfter` (24h) and `maxSocketLife` (12h). A home-region writer must be the only writer, or leases need a cross-cell authority.
  - `internal/repogroupprimary` (core's processing-primary election per repo group) is the nearest existing "one placement does it" mechanism. Strata routes deliberately use `placementNone`.
  - Writer identity is strata's random ID at `Announce`. Nothing ties it to a stable service identity, and nothing in a policy can name it.
  - One-shot pushes create 3 refs each and serialise on entiredb's per-repo `refdf` lock. That cost is unmeasured (strata ADR-0020, "Since: what is not yet known"). A durable writer avoids it.
  
  **(b) A projector that follows many stores per cell**
  - Catch-up happens only when someone reads. ADR 0005's 2026-10-10 amendment removed the background consumer, because it read cert-only and "entiredb admits entire-api cert-only on the repo API but not for git fetches". The ADR says it can return once entiredb admits entire-api's git reads.
  - `refstream` is at-most-once core NATS, subscribed per repo only while a viewer is connected. A projector needs a durable JetStream consumer on `repo_refs_v1`, filtered to `refs/strata/<meta>/`, like the ingest pipeline has. It also needs a periodic sweep as a backstop; `followed_at` on the cursor table could drive it.
  - The per-store advisory lock already serialises ticks across replicas. With one lock per (repo, store), the keys are FNV-hashed into an int32, so collisions are possible but only cost waiting.
  - Cross-cell constraints:

  - `tick` is not indexed, which is fine for small stores (ADR 0009).
  
  **(c) Authorisation of strata pushes in entiredb**
  - `refs/strata/` is neither reserved nor hidden in `entiredb/refpolicy/refpolicy.go:221-345`. Anyone with repo `pull` can fetch it and anyone with `push` can rewrite any writer's refs.
  - strata ships a per-writer policy: `authz.Check`/`Grant`/`allow-oneshot` (`strata/authz/policy.go:159,221`), applied by `cmd/strata-receive` as a pre-receive hook (ADR-0012, ADR-0018). entiredb's go-git receive-pack (`entiredb/server/githttp/receive_pack.go:502-548`) does not call it.   | Plugin installation | `installations` (475) | the project's region (ADR `20261023-plugin-installation-issuer-is-project-jurisdiction.md`) | GLOBAL | Home core |
  | Billing | `billing_accounts` (017), `billing_ensured` (008), `billing_restrictions` (009) | subject home | GLOBAL | Home core |
  
  No core metadata entity is REGIONAL BY ROW keyed on its home. The REGIONAL BY ROW tables are mirror and outbox tables, keyed on a hidden `crdb_region`: `email_outbox`, `mirror_*`, `native_mirror_*_outbox`, `github_user_tokens`, `github_mirror_reconcile_attempts`. In practice everything is GLOBAL (for read locality) or pinned to the US primary.
  
  ## (c) Write flows and SpiceDB coupling
  
  All in `core/resource/store.go` unless noted. SQL and SpiceDB are never in one transaction. Each flow picks an order and compensates afterwards.
  
  - **CreateOrg** (219-374)
    - SpiceDB `OrgCreated` goes **first** (297).
    - Then one implicit-transaction CTE (247-278) does: quota count over memberships×orgs, the `accounts.org_creations`/`org_creation_limit` ledger, `INSERT orgs`, the owner `INSERT memberships` with `zed_token`, and an `UPDATE accounts` bump.
    - It runs a capability check pinned to the SpiceDB revision in parallel.
    - On failure: rollback (`rollbackOrgCreationAuthz`, 400-410) and ambiguous-commit resolution (337-353).
  - **CreateProject** (2866-2990)
    - SpiceDB `ProjectCreated` **first** (2909).
    - Then a CTE (2784-2830) checks the owner org exists, counts the per-owner quota, reads a live `reserved_name_grants` row, inserts `projects` (global unique `lower(name)`), and consumes the grant.
    - Compensation: `ProjectDeleted` (2994-3007, retry budget 3007-3040).
  - **DeleteProject** (3741-3890)
    - One transaction: `FOR UPDATE` check of repo groups, `DELETE project_permissions`, `plugins.EnqueueProjectDeleted` (writes `installation_event_outbox`), `DELETE projects`.
    - SpiceDB `ProjectDeleted` runs **after** commit. A failure is logged and swallowed (3875-3887).
  - **DeleteOrg** (1640-1780)
    - One transaction: count owned projects, delete memberships, bump `accounts.memberships_version` for every member, delete the org. It retries on 40001.
    - Afterwards: SpiceDB `MembershipRevoked` per member, then `OrgDeleted` (1686-1697).
  - **AddMember** (1820-1910)
    - Inside a transaction: `INSERT memberships` plus `UPDATE accounts` (1820-1830).
    - Then SpiceDB `MembershipGranted` while the transaction is still open.
    - Then it stamps `memberships.zed_token` and commits.
    - On failure: ambiguous-commit reconcile (2232-2260) and role-change reconcile (2190-2230).
    - The account counter bump (92-107) means **every membership write also writes the account row**.
  - **GrantProjectAccess / RevokeProjectAccess** (3648-3739)
    - SQL upsert or delete **first**, then SpiceDB `ProjectPermissionGranted` / `Revoked`. There is no compensation.
  - **GrantRepoAccess** (6415-6461)
    - Resolves the repo group, then SpiceDB `GroupOnlyRoleGranted` **first** ("SpiceDB … is the truth"), then the `repo_permissions` projection.
    - It skips github-forge and native-mirror groups, which are mirrorperms-owned.
  - **Repo create** (`core/regional/repos.go:160-215`)
    - Regional `INSERT repos` (regional DB).
    - Then SpiceDB `RepoCreatedWithGroup` (194).
    - Then global `PublishRepo` (`store.go:3914-4000`), a transaction that locks `repo_group`, adopts the owning project and inserts `repo_registry`.
    - If publish fails, `RepoCreationRolledBack` runs (206).
    - That is three stores with no shared transaction.
  - **Teams:** `TeamCreated`, `TeamDeleted` and `TeamMember*` at 2633-2753. They come from WorkOS.
  - **Repo detach and rename:** use `outbox.EnqueueInTx` (`core/repodetach/outbox.go:96-112`, `core/resource/repo_renamed.go:63`).
  
  After commit, handlers write the domain audit and call `LifecycleEvents().Publish`, which is best-effort NATS. Examples: `projects.go:187-188,513-518,777-783`, `orgs.go:109-110`.

  Outbox-like work queues that are not named "outbox": `trust_intents`, `mirror_url_dataplane_ops` (ADR `20260825-mirror-url-dataplane-outbox.md`), `repo_dataplane_cleanup_ops` (regional 034), `native_mirror_requests`, `github_org_membership_work`, `mirror_author_backfills`.
  
  **The common pattern:**
  1. The producer writes the row in the **same transaction** as the domain change. The domain change is the retry anchor.
  2. The key is natural and idempotent (`repo_id`, `(repo_id, op)`, `(installation_id, revision)`, event ULID), with `ON CONFLICT` rules.
  3. A routing column (`jurisdiction` / `home_jurisdiction`) is indexed with `created_at`, and a relay in each region drains only its own rows.
  4. Relays poll every 1s to 60s and claim with `FOR UPDATE SKIP LOCKED`, `lock_timeout`, or no lock with dedup.
  5. They publish with an acknowledged JetStream publish and a `Nats-Msg-Id`.
  6. They delete after the ack, inside the claiming transaction, on a detached 5s commit grace.
  7. Delivery is at-least-once and consumers must be idempotent.
  8. A failure skips only that row, so one poison row cannot block the batch.
  9. Retry rows use `attempts` and `next_attempt_at`.
  10. Every relay exports backlog and oldest-age gauges.
  
  Ordering is global `created_at` order, except the installation relay, which has per-entity revision ordering. That relay, plus the erasure multi-ack, is the closest existing template for a per-entity sequenced CRDB → strata relay.
  
  The gap for such a relay: org, project, membership, team and grant writes have no outbox at all. You would need either new `EnqueueInTx` calls in the `core/resource` write paths, or CRDB changefeeds, which are unused today.
  
  ## (e) Data that needs a global arbiter
  
  **Global name uniqueness:**
  - `handles`: `UNIQUE(provider, handle)` and PK `(provider, provider_user_id)` (squash 28-48).
  - `account_usernames`: PK `username_norm`, one live per account. Names stay held after erasure (208-218; `core/identity/store.go` DeleteAccount).
  - `projects_lower_name_key`: project names are globally unique (283; ADR `20260522-global-project-names.md`).
  - `orgs`: only system `:` names are unique (228). Human org names are **not** unique.
  - `orgs_workos_organization_id_key`; `github_org_links.github_org_id` (384).
  - `reserved_name_grants`: one open grant per `(scope, name)` (444). A project create consumes it atomically (`store.go:2784-2814`).
  - `plugins` slug, issuer and `jwks_url`; `plugin_public_keys`; `workload_identity_providers` name and issuer.
  - `repo_group(forge, data_primary_repo_id)`: one group per upstream, across all projects (320).
  - `repo_urls.url` PK; `github_address_tombstones(owner_login, repo_name)`.
  - `clusters`: unique slug and one default per jurisdiction (374-375).
  
  **Quotas and counters that span entities and regions:**
  - Owner orgs per account, limit 3. It counts memberships joined to orgs across all regions (`store.go:50,247-262`).
  - Lifetime cap `accounts.org_creations` / `org_creation_limit` (migrations 031/033) and `orgs.creation_ordinal` (032).
  - Projects per owner, limit 5 (`store.go:53`). It counts all projects of the owner, and an org's projects can be homed in any region.
  - `accounts.memberships_version`, the ETag counter that every org's membership writes bump.
  
  **Org-scoped constraints** (single-writer if they live with the org): `memberships(account_id, org_id)`, `teams(org_id, name)`, `service_accounts(org_id, name)`. Project-scoped: `repo_group(owning_project_id, lower(full_name))`.
  
  **Billing and policy:**
  - `billing_accounts` (unique subject), `billing_purchases` (idempotency key, one pending), `billing_ensured`, `billing_restrictions`.
  - `runner_policy` (singleton) and `runner_denials`.
  - `entire_data_primary_lease` (per jurisdiction).
  - `erasure_requests` (one open per subject) and `erasure_tombstones`.
  
  ## (f) Erasure requirements
  
  Main code is `core/api/account_delete.go`; the design is in ADRs `20260708-account-erasure-crdb-polled-outbox.md` and `20260717-account-erasure-architecture.md`.
  
  **Steps:**
  1. Request sets `deletion_requested_at` and revokes sessions (103).
  2. After a cooldown, the global reaper cronjob in us-east-2 runs `FinalizeAccountDeleteCore` (~290-570):
     - Ownership gate: an org owner blocks deletion.
     - It claims the account (`deletion_started_at`).
     - It opens a ledger request.
     - `unlinkAccountGrants` (583-640) calls `RevokeProjectAccess`, `RevokeRepoAccess` and `RemoveMember` on **any** project, repo or org, including ones homed elsewhere.
     - SpiceDB `AccountDeleted` purges every tuple where the account is the subject (one global write).
     - It erases federation bindings.
     - It deletes account-owned projects. `ErrHasRepos` is tolerated because some repos may be in foreign regions.
     - It writes the domain audit `account_deleted`.
     - `identity.DeleteAccount` deletes credentials, `public_profiles`, handles and accounts. It sets `account_usernames.account_id` to `''`, so the name stays held. This runs in the **same transaction** as the `account_erasure_outbox` enqueue.
     - It writes a `user.deleted` event (at-most-once) and an `erasure_tombstones` row (GLOBAL, hashed) to block resurrection.
  3. Each regional core runs `EraseAccountRegion` (643-). It deletes regional PII, deletes repos in its own clusters, revokes GitHub tokens, and sweeps personal projects. It is idempotent, keyed on the account ULID, and works after the global row is gone. The outbox row is deleted when all jurisdictions have acked.
  4. The third-party ledger is drained by a separate cronjob.
  
  **What survives today:**
  - `domain_audit_events.actor_account_id` (no FK).
  - Audit metadata that can carry `provider_user_id`, such as grant events (`projects.go:777-782`).
  - Held usernames.
  - The ledger `subject_key`.
  
  **Other PII in replicated metadata:**
  - `handles.email`, `handles.avatar_url`, `handles.handle`.
  - `public_profiles.display_name`.
  - `github_email_identities`.
  - `billing_accounts.display_name`, which may hold work emails (comment in 017).
  - `mirror_requests.account_id` and `native_mirrors.created_by_account_id`.
  - Every grant and membership row, keyed by account id.
  
  **What a replicated git record store must support:**
  - Real removal of PII from history: rewrite, crypto-shredding, or keeping PII out of the store.
  - Cascading writes into records owned by other entities in other home regions (grants and memberships). This breaks one writer per entity unless erasure is modelled as a request to each owning home.
  - Idempotent per-region erasure, with completion tracking across every region.
  - A tombstone that blocks resurrection.
  - Identity delete as the last, atomic step.
  - A path for removing SpiceDB tuples.
  
  The ADR invariants say identity is deleted last and nothing may be reported erased before the delete actually succeeds (ADR 20260717 lines 37-45).
