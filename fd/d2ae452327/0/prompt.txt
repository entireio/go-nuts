  ### 1. `ctx.Err() != nil` is an ambiguous shutdown signal — a per-attempt timeout is read as "shutdown" (design, medium-high) — SUSPECT (code paths verified, no production call site currently trips it)
  
  `backoff/backoff.go:155` and `jsconsumer/retry.go:1023` branch on `ctx.Err() != nil`, but any derived ctx qualifies: `context.WithTimeout(ctx, opTimeout)` per attempt, a deadline inherited from an RPC, a caller-side `WithCancel`. The drain-window cancellation and a per-message deadline are indistinguishable.
  
  Concrete failure: entiredb `repoops/consumer.go:485` already wraps the handler ctx in `opCtx` with a timeout; today it passes the outer `ctx` to `c.nak()` (safe), but one refactor that passes `opCtx` turns every "attempt timed out" (slow poison, the exact thing `TermOnExhaustion` exists for) into: NakOrTerm never Terms → message left un-acked on a work-queue stream forever. For `Retry.Settle`: a timed-out attempt on the ladder-spent delivery defers to the broker cap, silently spending the `CaptureReserve` delivery, and (see #6) spends the breaker's quarantine budget without acting.
  
  Fix: make the scaffold's cancellation identifiable. In `Start` use `context.WithCancelCause`, cancel with an exported sentinel (it cannot live in `jsconsumer` because `backoff` is imported by it — put it in `backoff` or `natsmsg`, e.g. `natsmsg.ErrDrainElapsed`), and have `NakOrTerm`/`Settle` check `errors.Is(context.Cause(ctx), sentinel)` rather than `ctx.Err() != nil`. If you keep `ctx.Err()`, say in both docs, loudly, "pass the context the scaffold gave you, not a per-attempt derivative".
  
  ### 2. Doc overclaim on the join-timeout margin (doc, medium) — VERIFIED constants
  
  `jsconsumer/jsconsumer.go:80-82`: "under nuts.DefaultJoinTimeout so a ShutdownGroup on defaults *never* drains a connection beneath a handler still inside its window". The margin is 5s (15s − 10s), but after the window the handler still has to *return*, and the post-cancel work this change itself routes it into is not 5s-bounded: `Retry.Settle` at the broker cap runs `capture` (dlqPublishTimeout = 15s, `natsmsg/deadletter.go:31`) + `DoubleAck` (dlqAckTimeout = 15s, `retry.go:42`) on `WithoutCancel`.   ### 3. No lever to abort the window early (API design, medium) — VERIFIED by reading
  
  Before this change, cancelling the ctx was the abort. Now, once `cc.Stop()` returns, nothing can cancel the handler ctx before `DrainWindow` elapses: a second SIGTERM, a preStop hook noticing the grace deadline, or a ShutdownGroup join timeout all just wait. `cancelHandlers` is private and only reachable through `stop.Do`. Suggest `Runner.Abort()` (cancel handlers now, then join) or `Stop` honouring a ctx. Worth deciding before the v0 break lands, since adding it later is another API churn across 28 call sites.
  
  ### 4. Additive windows when consumers are stopped sequentially (rollout risk, medium) — SUSPECT
  
  entire-api wires `stop = func() error { return errors.Join(cons.Stop(), lifecycle.Stop()) }` (`internal/server/server.go:442`), i.e. sequential Stops. Each `Runner.Stop` can now block its own full window, so N slow handlers cost N×10s instead of ~0 (previously every handler failed instantly on ctx.Canceled). Not a go-nuts bug, but the PR should state the requirement "stop Runners concurrently" and the adopting repos should be checked. entiredb's `bgCancel(); waitBounded(&bg, 15s)` is concurrent and fine.
  
  ### 5. AckWait vs DrainWindow without KeepInProgress (semantic, low-medium) — VERIFIED by reading, untested
  
  The window encourages handlers to run through SIGTERM. With `KeepInProgress` off and `AckWait < DrainWindow` (AckWait is configurable; default 30s is fine), the broker redelivers the in-flight message to a surviving replica while this one is still inside its window, so the shutdown case now produces concurrent duplicate processing and a late Ack that lands on a redelivered sequence. Suggest a `validate()` rejection or Warn when `EffectiveDrainWindow() > EffectiveAckWait() && !KeepInProgress`, and a sentence in the DrainWindow doc. KeepInProgress itself interacts fine: it is wall-clock driven, keeps extending for the whole window (cap 15 ticks × AckWait/3 = 5×AckWait), and `Process` stops it after `handle` returns.
  
  ### 6. `shouldQuarantine` spends the quarantine budget before the deferral decision (semantic, low) — VERIFIED by reading
  
  `retry.go:885` calls `spendQuarantineBudgetLocked` inside `shouldQuarantine`, which runs before the `ctx.Err()` check at `:1023`. On a deferred breaker branch the budget is consumed with no capture. Harmless when the process dies, but a Runner stopped and re-Started in-process (entire-api consumers have `Stop()` methods and `Retry.attach` is re-run on the same object) leaves the breaker silent for a full stall window. Fix: evaluate the deferral first (it only needs `delivered` and `ctx`), or refund the budget on the deferred path.
  
  ### 7. `FloorMonitor.pollFloor` still runs on the parent ctx (semantic, low) — VERIFIED
  
  `jsconsumer.go:636` passes `ctx`; the poll stops the instant the parent is cancelled while the handler keeps running up to 10s on a live ctx. `Settle` during that window can enforce the breaker on a floor reading that is up to (pollInterval + window) stale. Pass `handlerCtx` instead — `pollFloor` already stops on `r.closed`, so nothing leaks.
  
  ### 8. The Warn can fire with no handler in flight (log accuracy, low) — VERIFIED via nats.go
  
  `r.closed` is `closedCh`, closed by the subscription's closed handler after `waitForMsgs` exits (nats.go v1.52.0 `nats.go:3571-3660`, `pull.go:286-299`), so normally it fires right after `Unsubscribe`. But `Subscription.Unsubscribe` returns `ErrConnectionDraining` *without* removing the sub when the connection is already draining (`nats.go:5181-5200`); `closedCh` then closes only when the drain finishes. If a caller violates the ordering (drains nc before/concurrently with Stop), `windowElapsed` wins and `jsconsumer.go:505` logs "cancelling in-flight handler" with none in flight. Cheap fix: an atomic in-flight flag set around `onMsg(handlerCtx, m)`; log only when set (and the message is more honest either way). Timer does not leak (`windowElapsed` defers `timer.Stop()`), and the boundary case (handler returns as the timer fires) is correctly preferred to "done".
